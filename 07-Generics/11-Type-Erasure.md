# 11 — Type Erasure

> **Type erasure is the mechanism Java uses to implement generics while maintaining compatibility with older Java code. Generic type information is primarily used by the compiler and is erased from most generic types at runtime.**

# 1. Introduction

Java Generics allow us to write type-safe code.

Example:

    List<String> names = new ArrayList<>();

The compiler knows:

    names

should contain:

    String

However, Java's JVM runtime historically operates without the full generic type information of ordinary parameterized types.

Java solves this using:

    Type Erasure

The compiler uses generic information for:

    Type checking
    Type inference
    Compile-time safety

and then removes or transforms most generic type information before runtime.

---

# 2. Why Type Erasure Exists

Generics were introduced in:

    Java 5

Before generics existed, Java collections commonly used:

    Object

Example:

    List list = new ArrayList();

    list.add("Java");

    String value = (String) list.get(0);

Generics improved this:

    List<String> list = new ArrayList<>();

    list.add("Java");

    String value = list.get(0);

The important requirement was:

> Existing pre-generics Java bytecode and libraries should continue to work with newer Java code.

This backward compatibility requirement was one of the major reasons Java generics were implemented through type erasure rather than a completely new runtime generic type system.

---

# 3. What Is Type Erasure

Type erasure means that generic type parameters are removed or replaced during compilation according to Java's erasure rules.

For example:

    class Box<T> {

        private T value;

        public void set(T value) {
            this.value = value;
        }

        public T get() {
            return value;
        }
    }

After erasure, conceptually:

    class Box {

        private Object value;

        public void set(Object value) {
            this.value = value;
        }

        public Object get() {
            return value;
        }
    }

This is a conceptual representation of erasure.

The actual generated bytecode contains additional compiler-generated details where necessary.

---

# 4. Compile-Time vs Runtime

This is one of the most important concepts.

    Source Code
         ↓
    Generic Type Information
         ↓
       Compiler
         ↓
    Type Checking
         ↓
    Type Erasure / Translation
         ↓
      Bytecode
         ↓
        JVM
         ↓
       Runtime

Generics provide strong type checking primarily at compile time.

---

## Example

    List<String> names = new ArrayList<>();

The compiler knows:

    String

is the intended element type.

Therefore this is rejected:

    names.add(100);

The error happens during:

    Compilation

not because the JVM dynamically checks:

    "Is this Integer allowed in List<String>?"

---

# 5. Simple Example

Consider:

    class Box<T> {

        private T value;

        public Box(T value) {
            this.value = value;
        }

        public T getValue() {
            return value;
        }
    }

Usage:

    Box<String> box =
            new Box<>("Java");

    String value = box.getValue();

The source code says:

    T → String

Conceptually, after erasure:

    class Box {

        private Object value;

        public Box(Object value) {
            this.value = value;
        }

        public Object getValue() {
            return value;
        }
    }

But the compiler inserts a cast at the use site:

    String value =
            (String) box.getValue();

The cast is generated by the compiler to preserve the type-safe behavior expected by the source program.

---

# 6. Erasure of Generic Classes

Consider:

    class Box<T> {

        T value;

        void set(T value) {
            this.value = value;
        }

        T get() {
            return value;
        }
    }

The unbounded type parameter:

    T

has an erasure of:

    Object

Conceptually:

    class Box {

        Object value;

        void set(Object value) {
            this.value = value;
        }

        Object get() {
            return value;
        }
    }

---

## Important

This does NOT mean:

    Box<String>

and:

    Box<Integer>

become different runtime classes.

Both are based on the same runtime class:

    Box

Therefore:

    Box<String>.class

is invalid.

You cannot write:

    Box<String>.class

Instead:

    Box.class

represents the runtime class.

---

# 7. Erasure of Generic Methods

Consider:

    public static <T> T identity(T value) {
        return value;
    }

Because `T` has no bound, its erasure is:

    Object

Conceptually:

    public static Object identity(Object value) {
        return value;
    }

The compiler performs the necessary casts at the calling location.

Example:

    String name =
            identity("Java");

Conceptually:

    String name =
            (String) identity("Java");

---

# 8. Erasure of Bounded Type Parameters

Consider:

    class Box<T extends Number> {

        private T value;

        public T getValue() {
            return value;
        }
    }

Here:

    T extends Number

Therefore the erasure of `T` is:

    Number

Conceptually:

    class Box {

        private Number value;

        public Number getValue() {
            return value;
        }
    }

---

## Important Rule

For an unbounded type parameter:

    <T>

erasure:

    Object

For:

    <T extends SomeClass>

erasure:

    SomeClass

The first bound determines the erasure.

---

# 9. Erasure of Multiple Bounds

Consider:

    <T extends Number & Comparable<T>>

There are two bounds:

    Number
    Comparable<T>

The erasure is based on the first bound:

    Number

Conceptually:

    <T extends Number & Comparable<T>>

becomes:

    Number

for the erased type.

Therefore the order matters.

Valid:

    <T extends Number & Comparable<T>>

The class bound must come before interface bounds.

---

# 10. Compiler-Generated Casts

This is one of the most important effects of type erasure.

Consider:

    List<String> names =
            new ArrayList<>();

    names.add("Java");

    String name = names.get(0);

At source level:

    get()

appears to return:

    String

But after erasure, the underlying collection method returns:

    Object

The compiler effectively inserts:

    String name =
            (String) names.get(0);

This cast is generated by the compiler.

---

## Why Does This Work?

Because the compiler already verified:

    names

is a:

    List<String>

and normal generic operations are type checked.

Therefore the generated cast is expected to succeed for correctly typed code.

---

# 11. Type Erasure and Bytecode

You can inspect generated bytecode using tools such as:

    javap

For example:

    javac Box.java

then:

    javap -c Box

The bytecode can show:

    Object

where the source code used an unbounded generic type parameter.

For a call such as:

    String value = box.getValue();

you may see a runtime cast instruction such as:

    checkcast java/lang/String

The important flow is:

    Generic Source
          ↓
       Compiler
          ↓
      Erasure
          ↓
    Bytecode
          ↓
    Runtime Casts where required

# 12. Type Erasure and Raw Types

Raw types are closely related to type erasure.

Example:

    List list = new ArrayList();

This is a raw type.

The generic information:

    <String>

is absent from the declaration.

Compare:

    List<String> names;

with:

    List names;

The first provides compile-time type checking.

The second bypasses much of that generic checking.

---

## Example

    List<String> names =
            new ArrayList<>();

    names.add("Java");

This is safe.

But:

    List raw = names;

    raw.add(100);

Now the list has been accessed through a raw type.

This can produce:

    unchecked warning

and later potentially:

    ClassCastException

when retrieving the element through the parameterized reference.

---

# 13. Why Generic Type Is Not Available at Runtime

Consider:

    List<String> strings =
            new ArrayList<>();

    List<Integer> integers =
            new ArrayList<>();

At runtime, the generic arguments are erased for ordinary parameterized types.

Therefore:

    strings.getClass()

and:

    integers.getClass()

refer to the same runtime class:

    ArrayList

So this is true:

    strings.getClass() == integers.getClass()

The runtime does not normally distinguish:

    ArrayList<String>

from:

    ArrayList<Integer>

as separate runtime classes.

---

# 14. Why Cannot Create `new T()`

Consider:

    class Box<T> {

        T create() {
            return new T();
        }
    }

This is invalid.

Why?

Because after erasure:

    T

could become:

    Object

or another bound.

The JVM cannot simply know which concrete class should be instantiated.

For example:

    Box<String>

would need:

    new String()

while:

    Box<Integer>

would need:

    new Integer(...)

There is no runtime class information for `T` that would make:

    new T()

generally possible.

---

## Common Solution

Pass a factory or `Class<T>` when appropriate.

Example:

    class Factory<T> {

        private Class<T> type;

        Factory(Class<T> type) {
            this.type = type;
        }

        T create()
                throws InstantiationException,
                       IllegalAccessException {

            return type.getDeclaredConstructor()
                       .newInstance();
        }
    }

Modern code should generally prefer an appropriate factory such as:

    Supplier<T>

when construction is needed.

Example:

    class Factory<T> {

        private Supplier<T> supplier;

        Factory(Supplier<T> supplier) {
            this.supplier = supplier;
        }

        T create() {
            return supplier.get();
        }
    }

---

# 15. Why Cannot Create Generic Arrays

This is invalid:

    T[] array = new T[10];

Why?

Because arrays know their component type at runtime.

For example:

    String[] names = new String[10];

The runtime knows:

    String[]

But because generic type arguments are erased, the runtime generally cannot know:

    T[]

means:

    String[]

or:

    Integer[]

or:

    Employee[]

Therefore Java does not allow direct creation of:

    new T[10]

---

## What About Object[]?

Sometimes code uses:

    Object[] array = new Object[10];

and performs an unchecked cast.

Example:

    @SuppressWarnings("unchecked")
    T[] array = (T[]) new Object[10];

But this must be handled carefully because the runtime array type is actually:

    Object[]

This is one reason generic collections such as:

    ArrayList<T>

are generally preferred over generic arrays.

---

# 16. Why Cannot Use `instanceof List<String>`

This is invalid:

    if (value instanceof List<String>) {
    }

Why?

Because at runtime the JVM cannot distinguish:

    List<String>

from:

    List<Integer>

due to type erasure.

Therefore Java allows:

    if (value instanceof List<?>) {
    }

because:

    List<?>

is a reifiable type.

---

## Valid

    if (value instanceof List<?>) {
        System.out.println("It is a List");
    }

---

## Invalid

    if (value instanceof List<String>) {
        // Compile-time error
    }

---

# 17. Static Members and Type Parameters

Consider:

    class Box<T> {

        static T value;
    }

This is invalid.

Why?

Because static members belong to the class itself, not to a particular generic instance.

There is only one:

    Box.value

not a separate static field for:

    Box<String>

and:

    Box<Integer>

---

## Important

This is invalid:

    class Box<T> {

        static T value;
    }

But this is valid:

    class Box<T> {

        T value;
    }

because `value` belongs to each instance.

---

## Generic Static Method

A static method can declare its own type parameter:

    class Utility {

        public static <T> T identity(T value) {
            return value;
        }
    }

Here `T` belongs to the method, not the class.

---

# 18. Method Overloading and Erasure

Type erasure can create problems with method overloading.

Consider:

    void process(List<String> list) {
    }

    void process(List<Integer> list) {
    }

This is invalid.

Why?

After erasure both signatures become conceptually:

    void process(List list)

Therefore the methods would have the same signature.

The compiler reports a:

    name clash

---

## Important

You cannot overload methods only by changing generic type arguments.

Invalid:

    process(List<String>)

and:

    process(List<Integer>)

because both erase to:

    process(List)

---

## Valid Example

You can overload if the erased signatures are different.

Example:

    void process(List<String> list) {
    }

    void process(Set<String> set) {
    }

Their raw parameter types are different:

    List
    Set

so there is no erasure conflict.

---

# 19. Bridge Methods

Type erasure can sometimes cause a subclass method to no longer have the exact erased signature required for overriding.

The Java compiler can generate a synthetic method called a:

    Bridge Method

Example:

    class Parent<T> {

        T get() {
            return null;
        }
    }

    class Child extends Parent<String> {

        @Override
        String get() {
            return "Java";
        }
    }

After erasure, the parent method is conceptually:

    Object get()

while the child method is:

    String get()

These do not have identical erased signatures.

The compiler can generate a synthetic bridge method in `Child` that effectively behaves like:

    Object get() {
        return get();
    }

The bridge method preserves polymorphism after type erasure.

Detailed bridge methods are covered in:

    12-Bridge-Methods.md

---

# 20. Type Erasure and Inheritance

Consider:

    class Parent<T> {

        T value;

        T getValue() {
            return value;
        }
    }

    class Child extends Parent<String> {
    }

The source-level relationship says:

    Child extends Parent<String>

But runtime representation is based on the erased generic class.

The compiler uses generic metadata and generated bytecode mechanisms to preserve type-safe behavior.

This is why:

    Child child = new Child();

    String value = child.getValue();

works even though the erased implementation may involve:

    Object

internally.

---

# 21. Type Erasure and Reflection

Generics are erased from ordinary runtime type usage, but Java class files can retain generic metadata in a `Signature` attribute.

Reflection can sometimes access this metadata.

Example:

    class Box<T> {

        T value;
    }

A reflective API can inspect the declared generic field type.

For example:

    Field field =
            Box.class.getDeclaredField("value");

    Type type =
            field.getGenericType();

The returned `Type` may contain generic information.

This is an important distinction:

    Runtime class representation
            ≠
    Complete absence of all generic metadata

Generic signatures can be stored as class-file metadata and exposed through reflection.

---

# 22. Reifiable vs Non-Reifiable Types

A type is **reifiable** when its runtime representation contains enough information to fully represent that type.

Examples of reifiable types include:

    String

    Object

    List<?>

    List

    int[]

    String[]

Parameterized types with concrete type arguments are generally non-reifiable:

    List<String>

    List<Integer>

    List<Employee>

because their type arguments are erased from the normal runtime representation.

---

## Important Comparison

    List<String>
        ↓
    Non-reifiable


    List<?>
        ↓
    Reifiable

That is why:

    value instanceof List<?>

is allowed, while:

    value instanceof List<String>

is not.

---

# 23. Heap Pollution

Heap pollution occurs when a variable of a parameterized type refers to an object that is not of the expected parameterized type.

Example:

    List<String> names =
            new ArrayList<>();

    List raw = names;

    raw.add(100);

Now the runtime list contains an Integer even though the parameterized reference expects String elements.

Later:

    String name = names.get(0);

may result in:

    ClassCastException

---

## Why Can This Happen?

Usually because of:

    Raw types
    Unchecked operations
    Unsafe casts
    Non-reifiable varargs

Generics normally protect us from these situations, but unsafe operations can bypass compile-time checks.

---

# 24. Internal Working

Let's understand the complete flow.

## Step 1 — Source Code

    List<String> names =
            new ArrayList<>();

    names.add("Java");

    String value = names.get(0);

---

## Step 2 — Compiler Type Checks

The compiler verifies:

    names

is:

    List<String>

Therefore:

    names.add("Java")

is valid.

But:

    names.add(100)

is rejected.

---

## Step 3 — Erasure

Generic type arguments are erased from the runtime representation.

Conceptually:

    List<String>

becomes:

    List

and:

    String

as the type parameter is no longer part of the ordinary runtime class identity.

---

## Step 4 — Compiler Inserts Cast

The source:

    String value = names.get(0);

is conceptually translated to something like:

    String value =
            (String) names.get(0);

---

## Step 5 — Bytecode

The compiler generates bytecode containing the appropriate method invocation and cast operations.

---

## Step 6 — JVM Runtime

The JVM executes the generated bytecode.

The generic type parameter itself is not being dynamically enforced as:

    List<String>

at runtime.

The compiler-generated casts and ordinary runtime type checks enforce the required behavior.

---

# 25. DSA Patterns

Type erasure is not an algorithmic pattern, but it is important when designing generic DSA implementations.

---

## Pattern 1 — Generic Stack

    class Stack<T> {

        private Object[] data;
        private int size;

        Stack(int capacity) {
            data = new Object[capacity];
        }

        public void push(T value) {
            data[size++] = value;
        }

        @SuppressWarnings("unchecked")
        public T pop() {
            return (T) data[--size];
        }
    }

The internal array cannot simply be:

    new T[capacity]

because of type erasure.

Therefore implementations often use:

    Object[]

with controlled casts.

---

## Pattern 2 — Generic Queue

    class Queue<T> {

        private Object[] data;
        private int front;
        private int rear;

        Queue(int capacity) {
            data = new Object[capacity];
        }

        public void add(T value) {
            data[rear++] = value;
        }

        @SuppressWarnings("unchecked")
        public T remove() {
            return (T) data[front++];
        }
    }

Again:

    new T[]

is not directly possible.

---

## Pattern 3 — Generic Node

    class Node<T> {

        T data;
        Node<T> next;

        Node(T data) {
            this.data = data;
        }
    }

This is useful for:

    Linked List
    Stack
    Queue
    Trees
    Graph structures

---

## Problem-Solving Connection

When creating generic DSA structures, remember:

    Generic array
         ↓
    Cannot directly create T[]
         ↓
    Common implementation
         ↓
    Object[] + controlled cast

---

# 26. Common Mistakes

## Mistake 1 — Saying Generics Exist Completely at Runtime

Generics are primarily a compile-time type system.

Runtime behavior is affected by erasure.

---

## Mistake 2 — Saying All Generic Information Completely Disappears

This is too simplistic.

Generic type arguments are erased from the ordinary runtime type representation, but generic signatures can remain in class-file metadata and can be exposed through reflection.

---

## Mistake 3 — Thinking `List<String>` and `List<Integer>` Are Different Runtime Classes

They are not.

Both are based on:

    List

and a concrete implementation such as:

    ArrayList

---

## Mistake 4 — Creating `new T()`

Invalid:

    T object = new T();

The runtime does not know the concrete type represented by `T`.

---

## Mistake 5 — Creating `new T[]`

Invalid:

    T[] array = new T[10];

Generic arrays cannot be directly created this way.

---

## Mistake 6 — Using `instanceof List<String>`

Invalid:

    value instanceof List<String>

Use:

    value instanceof List<?>

instead.

---

## Mistake 7 — Overloading Only by Generic Type

Invalid:

    process(List<String> list)

    process(List<Integer> list)

Both erase to:

    process(List)

# 28. Top 10 Interview Questions

## Q1. What is type erasure?

Type erasure is the mechanism by which Java's compiler removes or replaces generic type parameters according to erasure rules while generating bytecode.

---

## Q2. Why does Java use type erasure?

A major reason is backward compatibility with pre-generics Java libraries and bytecode.

---

## Q3. What does an unbounded generic type parameter erase to?

    Object

---

## Q4. What does `<T extends Number>` erase to?

    Number

The first bound is used for the erasure.

---

## Q5. Why can't we instantiate `T`?

Because the concrete runtime type represented by `T` is not generally available through ordinary generic type information after erasure.

---

## Q6. Why can't we create generic arrays?

Arrays require runtime component-type information, while generic type arguments are erased from ordinary runtime type identity.

---

## Q7. Why is `instanceof List<String>` illegal?

Because `List<String>` is non-reifiable and the JVM cannot distinguish it from other parameterized `List` types through ordinary runtime type checks.

---

## Q8. What is a bridge method?

A compiler-generated synthetic method that preserves polymorphism when generic inheritance and type erasure would otherwise cause an overriding method's erased signature to differ.

---

## Q9. What is heap pollution?

Heap pollution occurs when a parameterized variable refers to an object that is not compatible with its parameterized type, often due to raw types, unchecked operations, or unsafe casts.

---

## Q10. Does type erasure happen at runtime?

No.

Type erasure is a compiler-level transformation that occurs while compiling generic source code into bytecode.

# 29. 30-Second Interview Answer

> **Type erasure is how Java implements generics while maintaining compatibility with older Java code. The compiler uses generic information for compile-time type checking and then erases or replaces type parameters according to their bounds. An unbounded `T` generally erases to `Object`, while `T extends Number` erases to `Number`. The compiler may insert casts where necessary. Because of erasure, we cannot directly create `new T()`, `new T[]`, or use `instanceof List<String>`.**
