# 12 — Bridge Methods

> **Bridge methods are compiler-generated synthetic methods created by the Java compiler to preserve polymorphism when generics and type erasure cause a subclass method's erased signature to differ from the superclass method.**

# 1. Introduction

A bridge method is a method generated by the Java compiler.

It is usually:

- `synthetic`
- compiler-generated
- not explicitly written by the programmer
- used to preserve polymorphism
- strongly related to generics and type erasure

The main problem it solves is:

> After type erasure, a subclass method may no longer appear to override the superclass method correctly.

The compiler creates a bridge method to maintain the expected overriding behavior.

---

# 2. Why Bridge Methods Exist

Consider:

    class Parent<T> {

        T get() {
            return null;
        }
    }

Now create:

    class Child extends Parent<String> {

        @Override
        String get() {
            return "Java";
        }
    }

At source-code level:

    Parent<String>.get()
            ↓
        returns String

    Child.get()
            ↓
        returns String

Everything looks fine.

But type erasure changes the situation.

---

# 3. Connection With Type Erasure

For:

    class Parent<T>

the unbounded:

    T

erases to:

    Object

Therefore the parent method:

    T get()

conceptually becomes:

    Object get()

But the child method is:

    String get()

Now we have:

    Parent:
        Object get()

    Child:
        String get()

The erased signatures are no longer identical.

This creates a problem for overriding and polymorphism.

The compiler solves this by generating a bridge method.

---

# 4. Basic Example

Consider:

    class Parent<T> {

        T get() {
            return null;
        }
    }

    class Child extends Parent<String> {

        @Override
        String get() {
            return "Java";
        }
    }

Now:

    Child child = new Child();

    String value = child.get();

This works normally.

More importantly:

    Parent<String> parent = new Child();

    String value = parent.get();

This must also work.

Why?

Because Java supports runtime polymorphism.

The actual object is:

    Child

but the reference type is:

    Parent<String>

The JVM must still invoke the correct child implementation.

The bridge method helps preserve this behavior.

---

# 5. Step-by-Step Working

Let's follow the complete process.

## Step 1

We define:

    Parent<T>

with:

    T get()

---

## Step 2

We create:

    Child extends Parent<String>

Therefore:

    T = String

---

## Step 3

The child overrides:

    String get()

---

## Step 4

Type erasure changes the parent method conceptually into:

    Object get()

---

## Step 5

The child still has:

    String get()

---

## Step 6

The compiler detects that erasure has created a signature mismatch.

---

## Step 7

The compiler generates a bridge method approximately like:

    Object get() {
        return get();
    }

The actual bridge method is synthetic and contains the required compiler-generated behavior.

---

## Step 8

Now the erased parent contract can still be satisfied.

---

# 6. Parent Generic Class

Consider:

    class Parent<T> {

        T get() {
            return null;
        }
    }

The method:

    T get()

depends on the generic type parameter.

For:

    Parent<String>

the source-level return type becomes:

    String

For:

    Parent<Integer>

the source-level return type becomes:

    Integer

But the runtime erased representation uses the erasure of `T`.

Because `T` is unbounded:

    T → Object

---

# 7. Child Class

Now:

    class Child extends Parent<String> {

        @Override
        String get() {
            return "Java";
        }
    }

The child method returns:

    String

The parent method's erased return type is:

    Object

Therefore:

    Parent:
        Object get()

    Child:
        String get()

The compiler must preserve the overriding relationship.

---

# 8. What Happens After Erasure

Before erasure:

    Parent<T>

    T get()


    Child extends Parent<String>

    String get()

After erasure, conceptually:

    Parent

    Object get()


    Child

    String get()

Now the methods appear different.

Without compiler assistance, this could break polymorphism.

---

# 9. The Problem Created by Erasure

Suppose:

    Parent<String> parent =
            new Child();

Now:

    String value = parent.get();

The compiler knows that:

    Parent<String>.get()

returns:

    String

But the erased method is effectively:

    Object get()

At runtime, the JVM works with the erased method signatures.

The JVM needs a method compatible with:

    Object get()

inside the child class.

The compiler therefore generates one.

---

# 10. Compiler Solution

The compiler adds a bridge method.

Conceptually:

    class Child extends Parent<String> {

        String get() {
            return "Java";
        }

        // Compiler generated
        Object get() {
            return get();
        }
    }

The second method is the bridge method.

It delegates to:

    String get()

---

# 11. Generated Bridge Method

The generated bridge method can be thought of as:

    Object get() {
        return get();
    }

But the actual bytecode contains compiler-generated instructions and metadata.

It is typically marked:

    ACC_BRIDGE

and:

    ACC_SYNTHETIC

These are JVM-level method flags.

---

## What Does It Do?

Conceptually:

    Parent reference
          ↓
    bridge method
          ↓
    actual Child.get()
          ↓
       String
          ↓
       Object

Because String is an Object, the returned value can satisfy the erased parent signature.

---

# 12. Runtime Polymorphism

This is the most important reason bridge methods matter.

Consider:

    Parent<String> parent =
            new Child();

    String value = parent.get();

At compile time:

    parent.get()

is known as returning:

    String

At runtime:

    parent

actually refers to:

    Child

The JVM performs dynamic method dispatch.

The bridge method provides the erased signature expected by the parent.

Conceptually:

    Parent<String>
          │
          │ get()
          ▼
       Child
          │
          ▼
    bridge get()
          │
          ▼
    Child.get()
          │
          ▼
      "Java"

---

# 13. Bridge Method and Casting

Bridge methods may also contain compiler-generated casts.

Consider a generic setter:

    class Parent<T> {

        void set(T value) {
        }
    }

    class Child extends Parent<String> {

        @Override
        void set(String value) {
            System.out.println(value);
        }
    }

After erasure:

    Parent:

        void set(Object value)

    Child:

        void set(String value)

The compiler can generate a bridge method conceptually like:

    void set(Object value) {
        set((String) value);
    }

Now:

    Parent<String> parent =
            new Child();

    parent.set("Java");

works correctly.

If an incompatible object somehow reaches the erased bridge through an unsafe operation, the generated cast can result in:

    ClassCastException

---

# 14. Bridge Method vs Normal Method

| Bridge Method | Normal Method |
|---|---|
| Usually compiler-generated | Usually programmer-written |
| Usually synthetic | Normally not synthetic |
| Often created because of generics/type erasure | Created for application logic |
| Preserves polymorphism | Provides actual behavior |
| Can delegate to another method | Usually contains the actual implementation |
| May contain compiler-generated casts | May contain programmer-written casts |

---

# 15. Synthetic Methods

A synthetic method is a method generated by the compiler that is not directly present in the source code in the same form.

Bridge methods are commonly:

    synthetic

You can detect this through reflection.

Example:

    Method[] methods =
            Child.class.getDeclaredMethods();

    for (Method method : methods) {

        System.out.println(
                method.getName()
        );

        System.out.println(
                "Bridge: " +
                method.isBridge()
        );

        System.out.println(
                "Synthetic: " +
                method.isSynthetic()
        );
    }

A bridge method generally reports:

    isBridge() → true

and:

    isSynthetic() → true

---

# 16. How to See Bridge Methods

You can inspect compiled bytecode using:

    javap

Compile:

    javac Child.java

Then:

    javap -c -v Child

The output can reveal compiler-generated methods.

Look for flags such as:

    ACC_BRIDGE

and:

    ACC_SYNTHETIC

This is a useful way to understand what the compiler actually generated.

---

# 17. Reflection and Bridge Methods

Reflection provides:

    Method.isBridge()

to determine whether a method is a bridge method.

Example:

    for (Method method :
            Child.class.getDeclaredMethods()) {

        if (method.isBridge()) {
            System.out.println(
                    "Bridge method: "
                    + method.getName()
            );
        }
    }

There is also:

    method.isSynthetic()

which checks whether a method is synthetic.

---

## Important

Not every synthetic method is necessarily a bridge method.

But a bridge method is typically synthetic.

Therefore:

    isBridge()

is the direct check for bridge status.

---

# 18. Bridge Methods With Interfaces

Bridge methods can also appear when implementing generic interfaces.

Example:

    interface Processor<T> {

        T process(T value);
    }

Now:

    class StringProcessor
            implements Processor<String> {

        @Override
        public String process(String value) {
            return value.toUpperCase();
        }
    }

Source-level method:

    String process(String value)

After erasure, the interface method is conceptually:

    Object process(Object value)

The implementation still has:

    String process(String value)

The compiler may generate a bridge method conceptually:

    Object process(Object value) {
        return process((String) value);
    }

This preserves interface polymorphism after erasure.

---

# 19. Bridge Methods With Comparable

A classic real-world example is:

    Comparable<T>

Consider:

    class Student
            implements Comparable<Student> {

        private int marks;

        @Override
        public int compareTo(Student other) {
            return Integer.compare(
                    this.marks,
                    other.marks
            );
        }
    }

The source method is:

    compareTo(Student)

But the generic interface:

    Comparable<T>

erases conceptually to:

    Comparable

with:

    compareTo(Object)

Therefore the compiler can generate a bridge method conceptually like:

    public int compareTo(Object other) {

        return compareTo(
                (Student) other
        );
    }

This is one of the most common examples used to explain bridge methods.

---

# 20. Bridge Methods and Covariant Return Types

Bridge methods are also related to covariant return types.

Consider:

    class Parent {

        Object get() {
            return null;
        }
    }

    class Child extends Parent {

        @Override
        String get() {
            return "Java";
        }
    }

Here the child returns:

    String

while the parent returns:

    Object

This is a covariant return type.

Java allows the subclass to return a more specific reference type.

The compiler may generate a bridge method to maintain binary compatibility in situations involving differing erased method descriptors.

So bridge methods are not limited exclusively to generic code, although generics and type erasure are the most common reason they appear.

---

# 21. Bridge Methods and Type Erasure

The relationship can be summarized as:

    Generics
       ↓
    Type Erasure
       ↓
    Method signature mismatch
       ↓
    Overriding relationship could break
       ↓
    Compiler generates bridge method
       ↓
    Polymorphism preserved

---

    }

After erasure:

Let's understand the complete process.

---

## Step 2 — Generic Specialization

    class Child extends Parent<String> {

        @Override

            return "Java";
        }
    }

---

## Step 3 — Type Erasure

The parent:

    T get()

becomes conceptually:

    Object get()

---

## Step 4 — Signature Difference

Now:

    Parent:
        Object get()

    Child:
        String get()

---

The compiler needs the child to remain compatible with the erased parent contract.

---

## Step 6 — Bridge Generation

Compiler generates approximately:

    Object get() {

When code calls the method through the parent type, the child bridge method can receive the call and delegate to:

    String get()

# 23. DSA Connection

Bridge methods are not a DSA algorithm or pattern.

However, they can appear when creating generic data structures using inheritance.

---

## Example — Generic Node

    class Node<T> {

        T data;

        Node(T data) {
            this.data = data;
        }

        T getData() {
            return data;
        }
    }

A subclass can specialize it:

    class StringNode extends Node<String> {

        StringNode(String data) {
            super(data);
        }

        @Override
        String getData() {
            return super.getData();
        }
    }

Because of generic specialization and erasure, compiler-generated methods can be involved in maintaining overriding behavior.

---

## DSA Interview Connection

When you build:

    Generic LinkedList<T>
    Generic Stack<T>
    Generic Queue<T>
    Generic Tree<T>

you normally don't need to manually create bridge methods.

The compiler handles them automatically.

The important interview knowledge is understanding:

    Generic DSA structure
            ↓
        Type Erasure
            ↓
    Possible Bridge Method
            ↓
    Polymorphism preserved

# 24. Common Mistakes

## Mistake 1 — Thinking Bridge Methods Are Written Manually

Normally they are compiler-generated.

---

## Mistake 2 — Thinking Bridge Methods Are Regular Business Logic

No.

Their primary purpose is compatibility between:

    generic source code

and:

    erased runtime method signatures.

---

## Mistake 3 — Thinking Every Generic Method Creates a Bridge Method

No.

Bridge methods are generated only when necessary to preserve method overriding/polymorphism after erasure or in related compiler scenarios.

---

## Mistake 4 — Confusing Bridge With Synthetic

Bridge methods are usually synthetic, but the concepts are different.

    Synthetic
        ↓
    Compiler-generated artifact

    Bridge
        ↓
    Specific compiler-generated method
    used to preserve overriding compatibility

---

## Mistake 5 — Thinking Bridge Methods Are Visible in Source Code

Normally you will not see them in the source code.

You can observe them using:

    Reflection

or:

    javap

---

## Mistake 6 — Thinking the Bridge Contains the Actual Business Logic

Usually the bridge delegates to the actual method.

Example:

    Object get() {
        return get();
    }

The real implementation is:

    String get() {
        return "Java";
    }

# 26. Top 10 Interview Questions

## Q1. What is a bridge method?

A bridge method is a compiler-generated method used to preserve polymorphism when type erasure causes an overriding method's erased signature to differ from the parent method's erased signature.

---

## Q2. Why are bridge methods needed?

Because Java generics use type erasure.

After erasure, a child method may no longer have the same signature as the method it logically overrides.

The bridge restores compatibility.

---

## Q3. Are bridge methods generated by the compiler?

Yes.

The Java compiler generates them when necessary.

---

## Q4. What is the relationship between bridge methods and type erasure?

Type erasure can create a mismatch between the erased parent method and child implementation.

Bridge methods solve that mismatch.

---

## Q5. Are bridge methods visible in source code?

Normally no.

They are compiler-generated methods.

---

## Q6. How can you detect a bridge method?

Using reflection:

    method.isBridge()

---

## Q7. What is the difference between bridge and synthetic?

`Synthetic` describes compiler-generated members that are not directly represented in source code in the same form.

`Bridge` specifically identifies a compiler-generated method used to preserve overriding behavior.

A bridge method is generally synthetic.

---

## Q8. Can bridge methods contain casts?

Yes.

A bridge method may cast an erased parameter back to the specialized type before delegating to the real method.

---

## Q9. Give a classic bridge-method example.

A classic example is:

    class Student
            implements Comparable<Student>

The source method is:

    compareTo(Student)

while the erased interface method is conceptually:

    compareTo(Object)

The compiler can generate a bridge:

    compareTo(Object)

that casts to Student and delegates to:

    compareTo(Student)

---

## Q10. What is the purpose of bridge methods in one line?

> **Bridge methods preserve polymorphism after generic type erasure.**

# 27. 30-Second Interview Answer

> **A bridge method is a compiler-generated synthetic method created mainly because of generics and type erasure. Suppose a parent class has `T get()` and a child extends it with `String get()`. After erasure, the parent method becomes `Object get()`, while the child still has `String get()`. To preserve overriding and runtime polymorphism, the compiler generates a bridge method such as `Object get()` that delegates to the child's `String get()`. Bridge methods can be inspected using reflection with `isBridge()` or using `javap`.**
